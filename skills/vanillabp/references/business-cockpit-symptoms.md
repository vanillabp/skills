# From a symptom to the answer in the Business Cockpit

A developer searches with what they see, not with the name of the chapter that holds the
answer. This page does for the VanillaBP Business Cockpit what [symptoms.md](symptoms.md)
does for VanillaBP itself: it maps the messages and exceptions which come up around the
cockpit onto the place which explains them.

Read the *What you see* column like a search. Messages are shortened to the part worth
searching for, so match on the words rather than on the whole line. Where several rows fit,
read them in order: the first one is the common case.

The cockpit has two sides, and it helps to know which one a message comes from. A workflow
module reports into the cockpit, and what it says comes from the cockpit adapter of your BPMS.
The cockpit server stores those reports and serves the user interface. A message of a workflow
module names its BPMS and its adapter id, as in `Camunda8[default]: …`.

Some rows are about something you do not see. A task which never turns up in a list leaves no
error behind, so the row names the DEBUG line which says why it was dropped. Set the logger
`io.vanillabp.cockpit` to `DEBUG` before you go looking.

The last group holds problems the cockpit does not cause. They come up so often in its
neighbourhood that leaving them out would send people to Stack Overflow for an answer that
exists here.

Keep this list growing. A change which introduces a new message or a new startup check adds
its row here, next to the section it wrote.

## While a workflow module starts

| What you see | What it is | Where it is answered |
|---|---|---|
| `The Business Cockpit adapter is on the classpath but its configuration is incomplete`, with one `-` line per gap | Every gap of the application is named in one boot, and each line names the key which fills it. | [Connecting a workflow module](https://github.com/vanillabp/business-cockpit/wiki/Connecting-a-workflow-module#the-smallest-configuration-which-works) |
| `No transport to the cockpit server is configured`, or `Both transports … are configured, and events would be reported twice` | A module reports over exactly one transport. Neither key and no transport bean of your own ends the boot, and so do both keys at once. | [Connecting a workflow module](https://github.com/vanillabp/business-cockpit/wiki/Connecting-a-workflow-module#rest-kafka-or-a-way-of-your-own) |
| A line saying the adapter reports through a bean of yours, so one of the transport keys is not read | Your `BusinessCockpitTransport` bean wins over both shipped transports. A key nobody reads is worse than no key, so the boot names it. | [Connecting a workflow module](https://github.com/vanillabp/business-cockpit/wiki/Connecting-a-workflow-module#rest-kafka-or-a-way-of-your-own) |
| `The Business Cockpit adapter has no settings for workflow module '…', so the module reports nothing` | That module wrote none of the cockpit keys. It is allowed, and the log says so instead of leaving you with two empty lists. | [Connecting a workflow module](https://github.com/vanillabp/business-cockpit/wiki/Connecting-a-workflow-module#the-smallest-configuration-which-works) |
| `'…' is none of the known UI URI types`, or a refusal naming `workflow-module-uri` or `ui-uri-path` | The three keys which say where your module answers and how its forms are served. | [The smallest configuration which works](https://github.com/vanillabp/business-cockpit/wiki/Connecting-a-workflow-module#the-smallest-configuration-which-works) |
| `Workflow module '…' left a setting of the Business Cockpit to its workflows, and one of them does not carry it` | A value may stand per module, per workflow, per user task, and the most specific one wins. Written one level down, every workflow of the module has to say it. | [Where a workflow module writes its keys](https://github.com/vanillabp/business-cockpit/wiki/Configuration#where-a-workflow-module-writes-its-keys) |
| `'…' is set to '…', and that says nothing about where the directory is` | `vanillabp.cockpit.template-loader-path` carries `classpath:` or `file:` in front of the path. Version 1 read a bare path as a directory of the file system. | [Migrating from version 1](https://github.com/vanillabp/business-cockpit/wiki/Migrating-from-version-1#what-behaves-differently) |
| `The directory '…' configured as the Business Cockpit's template loader path cannot be read` | The directory is opened while the application boots, not at the first report. Both sides of the cockpit read their template path the same way. | [What the cockpit server needs](https://github.com/vanillabp/business-cockpit/wiki/Configuration#what-the-cockpit-server-needs) |
| `The truststore '…' could not be read` | The PKCS12 file of the REST transport is opened at startup on purpose. `rest.ssl-truststore-password` has to be its password. | [Where the reports go](https://github.com/vanillabp/businesscockpit-camunda7-adapter/wiki/Configuration#where-the-reports-go) |
| On Quarkus the build ends with `The Business Cockpit adapter is configured with a key it does not read` | A key of version 1, a typo the message offers a correction for, or a key written at a level which does not read it. On Spring Boot such a key is ignored, so check by hand there. | [The keys which are gone](https://github.com/vanillabp/business-cockpit/wiki/Migrating-from-version-1#the-keys-which-are-gone), [Where a workflow module writes its keys](https://github.com/vanillabp/business-cockpit/wiki/Configuration#where-a-workflow-module-writes-its-keys) |
| The boot ends naming two `@UserTaskDetailsProvider` methods and the task they both claim | Two methods for one task, or two writing `*`, leave nothing to say which one to call. They may share a task only where their versions do not overlap. | [Describing one user task](https://github.com/vanillabp/business-cockpit/wiki/Reporting-workflows-and-user-tasks#describing-one-user-task) |
| `The … is annotated with @DetailsEvent but is not of type … DetailsEvent.Event` | A details provider declares the parameters it wants, and each recognized one has its type. | [What the method may ask for](https://github.com/vanillabp/business-cockpit/wiki/Reporting-workflows-and-user-tasks#what-the-method-may-ask-for) |
| `Two beans implementing WorkflowModuleDetailsProvider answer for the workflow module '…'` | One bean answers which groups may see a module, so let each module have one. | [Who may see a workflow module](https://github.com/vanillabp/business-cockpit/wiki/Reporting-workflows-and-user-tasks#who-may-see-a-workflow-module) |
| A WARN naming a details provider method which serves no deployed version | The method names a version of the model which is not deployed, so it waits for an event that never comes. A warning and not the end of the boot, because a rolling deployment looks like this for a while. | [Which versions of your model a method serves](https://github.com/vanillabp/business-cockpit/wiki/Reporting-workflows-and-user-tasks#which-versions-of-your-model-a-method-serves) |

## While a workflow module reports

| What you see | What it is | Where it is answered |
|---|---|---|
| `ObjectOptimisticLockingFailureException: Unexpected row count (expected row count 1 but was 0)` at the end of a method which only read | Your details provider changed the aggregate while `getUserTask` was answering, and a report of a remote engine wrote the same row in between. The update in the brackets is the giveaway. | [When a read fails on a version conflict](https://github.com/vanillabp/business-cockpit/wiki/Architecture#when-a-read-fails-on-a-version-conflict) |
| Work of your own on a case is gone, with no exception and no log line | A details provider which writes is a second writer beside your own code, and without a version attribute on the aggregate the later write wins in silence. | [The aggregate is there to be read](https://github.com/vanillabp/business-cockpit/wiki/Reporting-workflows-and-user-tasks#the-aggregate-is-there-to-be-read) |
| `Reporting … to the Business Cockpit needs a transaction, and the thread calling BusinessCockpitService runs none` | The report is written into the transaction of the change it is about. `@Transactional` on the method doing both is what gives it one, and reading needs none. | [Reporting a change from your own code](https://github.com/vanillabp/business-cockpit/wiki/Reporting-workflows-and-user-tasks#reporting-a-change-from-your-own-code) |
| `The Business Cockpit has no BPMS half for the adapter '…'` | The artifact of that BPMS is missing from your workflow module. The message names the three and the variant of your platform. | [The one dependency](https://github.com/vanillabp/business-cockpit/wiki/Connecting-a-workflow-module#the-one-dependency) |
| `The Business Cockpit adapter needs an outbox store`, or a refusal that it cannot tell which store an event belongs in | A report is written before it is sent, so version 2 needs an outbox in your application. The store is the one holding the workflow aggregate, which the workflow service declaring that BPMN process says. | [The dependency](https://github.com/vanillabp/business-cockpit/wiki/Migrating-from-version-1#the-dependency) |
| `The Business Cockpit cannot write its report about …: one of the values of the report cannot be turned into JSON` | The report is put together at the event and travels with the outbox entry, so every value a details provider sets has to be writable. | [Business data in a list column](https://github.com/vanillabp/business-cockpit/wiki/Reporting-workflows-and-user-tasks#business-data-in-a-list-column) |
| `The details of a Business Cockpit event have to be a map of named values`, or a value the protobuf shape has no place for | Same rule seen from the transport. Put the values into a map or into an object with named properties. | [Business data in a list column](https://github.com/vanillabp/business-cockpit/wiki/Reporting-workflows-and-user-tasks#business-data-in-a-list-column) |
| A WARN that an entry is reported `with its identifiers alone: the entry carries no report any more` | The entry waited longer than `vanillabp.outbox.retention`, or it lost its report to a crash. The cockpit keeps what the report before said. | [Decision 26](https://github.com/vanillabp/business-cockpit/blob/main/DECISIONS.md#26-the-report-is-built-at-the-event-and-travels-with-its-entry) |
| `PhaseTwoPermanentFailure` about an entry which carries bytes this version cannot read | Repeating it will not change that. Remove the entry from the outbox store. | [Decision 26](https://github.com/vanillabp/business-cockpit/blob/main/DECISIONS.md#26-the-report-is-built-at-the-event-and-travels-with-its-entry) |
| `The authorization server at '…' answered the token request of client '…' with …` | The client credentials flow could not fetch a token. The report waits and is sent again. The way to that server is configured on its own, below `rest.authentication.oauth`. | [Where the reports go](https://github.com/vanillabp/businesscockpit-camunda7-adapter/wiki/Configuration#where-the-reports-go) |
| `Could not render the template '…'` and a title which stayed as it was | A template which fails does not stop the report. A `java.time` value is the usual reason and needs `no.api.freemarker:freemarker-java8`. | [What a template is handed](https://github.com/vanillabp/business-cockpit/wiki/Templates#what-a-template-is-handed) |
| `getUserTask` answers an empty `Optional` | The BPMS does not know that task any more. | [Reading back what was reported](https://github.com/vanillabp/business-cockpit/wiki/Reporting-workflows-and-user-tasks#reading-back-what-was-reported) |
| A report arrives at the cockpit after the change which followed it | The outbox promises no order, so the cockpit weighs every report by the timestamp of its event and drops what is older than what it holds. | [The path a report takes](https://github.com/vanillabp/business-cockpit/wiki/Architecture#the-path-a-report-takes) |
| A burst of changes to one task arrives as one report | Where an entry of the same task is still waiting, the newer report takes its place. | [What behaves differently](https://github.com/vanillabp/business-cockpit/wiki/Migrating-from-version-1#what-behaves-differently) |
| Tasks in the cockpit which were not there under version 1 | Every user task of a deployed process is reported now. A provider decides how much is shown, not whether anything is shown. | [What behaves differently](https://github.com/vanillabp/business-cockpit/wiki/Migrating-from-version-1#what-behaves-differently) |

## Around the BPMS half

| What you see | What it is | Where it is answered |
|---|---|---|
| The boot ends naming the history level of a Camunda 7 engine and the events it does not write | Camunda 7: the cockpit reads a workflow's start, end and cancellation out of the engine's history. | A Camunda 7 report carries no version, and only a provider naming no version serves it | Camunda 7: somebody deleted a deployment while its history stayed, so the engine holds no definition to count. | [Which version the Camunda 7 adapter reports](https://github.com/vanillabp/businesscockpit-camunda7-adapter/wiki/Home#which-version-it-reports) |
| The cockpit shows a task the engine rolled back, or the other way round | Camunda 7: an engine on a data source of its own commits separately from your application, on both platforms. | A WARN that the cockpit `does not report job … wired no listener of that type for that process` | Camunda 8: the deployed model carries a listener the running version no longer adds. | A WARN that a listener job `carries no user-task properties` | Camunda 8: the report is written without the assignee, the candidates and the two dates. | A WARN that `the cluster's searchable storage holds no record of` a task or a workflow | Camunda 8: either the record is gone, or the exporter behind the engine has not caught up. A case born in the very transaction asking here looks like this. | [What the Camunda 8 adapter reads back](https://github.com/vanillabp/businesscockpit-camunda8-adapter/wiki/Home#what-it-reads-back) |
| A WARN after `aggregateChanged` that the storage holds no workflow of that aggregate | Camunda 8: the same lag, another caller. A call right after starting a workflow is superfluous, because the start-event listener reports it anyway. | [What the Camunda 8 cockpit shows differently](https://github.com/vanillabp/businesscockpit-camunda8-adapter/wiki/Migrating-from-version-1#what-the-cockpit-shows-differently) |
| The first deployment after the upgrade stores a new version of every process | Camunda 8: the cockpit puts an `end` listener on every start event, and the 8.10 build a `cancel` listener on the process. | The boot stops asking for `vanillabp.adapters.<id>.job-lease` | Camunda 8: on a release line which knows leases the adapter wants `use` or `do-not-use`. One answer serves the adapter's workers and the cockpit's. | [When a Camunda 8 report takes longer than its lock](https://github.com/vanillabp/businesscockpit-camunda8-adapter/wiki/Home#when-a-report-takes-longer-than-its-lock) |
| Workers of one application sit idle on listener jobs another application takes | Camunda 8: a lease is a ratchet, per job type. A job which went to a leasing worker never goes back to one without a lease. | [What a lease costs a rolling upgrade](https://github.com/vanillabp/businesscockpit-camunda8-adapter/wiki/Home#what-a-lease-costs-a-rolling-upgrade) |

| A case ended by a terminate end event or by an event subprocess is shown as completed | Camunda 8 and Camunda 7 answer alike: the model cleared the other tokens away and ran to its own end, and nothing ended it from the outside. | [What each Camunda 8 listener reports](https://github.com/vanillabp/businesscockpit-camunda8-adapter/wiki/Home#what-each-of-them-reports), [How the Camunda 7 adapter learns about workflows](https://github.com/vanillabp/businesscockpit-camunda7-adapter/wiki/Home#how-it-learns-about-workflows) |
| A called process shows up as a case of its own, and a WARN mentions the call hierarchy | Camunda 8 line 8.8 only: its jobs do not carry their root process instance, and the poll for it ran past `workflow-visibility-timeout`. From 8.9 the job says it. | [Decision 3](https://github.com/vanillabp/businesscockpit-camunda8-adapter/blob/main/DECISIONS.md#3-a-called-process-is-a-step-not-a-case---what-a-cancelled-workflow-reports-superseded-by-decision-11) |
| A refusal about `remembered-user-tasks` which is no number, not positive, or written per workflow module | Process-Engine-API: that memory is one per node and shared by every workflow module, so the key is read globally only. | [The one key of this half](https://github.com/vanillabp/businesscockpit-process-engine-api-adapter/wiki/Configuration#the-one-key-of-this-half) |
| A WARN that neither source knows a workflow or a user task of an aggregate | Process-Engine-API: it offers no way to search for the work of a business case, so this half answers from what this node was handed and from VanillaBP's delivery log. Said once per case. | [What the cockpit shows on this engine, and what it cannot](https://github.com/vanillabp/businesscockpit-process-engine-api-adapter/wiki/Home#what-the-cockpit-shows-and-what-it-cannot) |
| After a restart a user task stays open in the cockpit for good | Process-Engine-API: what a delivery said lives on one node. A fresh node can say nothing about a task it did not see delivered, so the end of that task is never reported. | [Gap 11](https://github.com/vanillabp/businesscockpit-process-engine-api-adapter/blob/main/GAPS.md#11-nothing-lets-a-fresh-node-rebuild-what-it-knew-about-a-user-task) |
| The same delivery error keeps coming back into the log | Process-Engine-API: your details provider runs on the engine's delivery thread, so a failure there fails the delivery and the engine offers the task again. Your `@WorkflowTask` method still ran. | [How a user task reaches the cockpit](https://github.com/vanillabp/businesscockpit-process-engine-api-adapter/wiki/Home#how-a-user-task-reaches-the-cockpit) |
| A details provider which names a version never runs on the Process-Engine-API | This engine has no repository and no version numbers. Only a version tag it writes into the meta map of a delivery can be matched. | [Which version this engine reports](https://github.com/vanillabp/businesscockpit-process-engine-api-adapter/wiki/Home#which-version-this-engine-reports-and-what-a-details-provider-may-do-with-it) |
| A task somebody completed in another task list shows up as cancelled | Process-Engine-API: the engine names the API which noticed the end, and the reference engine adapter says `delete` for that. | [What the cockpit shows on this engine, and what it cannot](https://github.com/vanillabp/businesscockpit-process-engine-api-adapter/wiki/Home#what-the-cockpit-shows-and-what-it-cannot) |

## In the browser

| What you see | What it is | Where it is answered |
|---|---|---|
| `BcUnauthorizedException` or `BcForbiddenException`, as HTTP 401 and 403 | Every list is a boundary. A task or a case the list would not show is reported as unknown, and an action on it changes nothing. | [Who sees which user task](https://github.com/vanillabp/business-cockpit/wiki/Security#who-sees-which-user-task) |
| A case you know the id of is answered as unknown | The cockpit answers a case you may not see the same way as one which was never reported, so the answer tells nobody that it exists. | [Who sees which workflow](https://github.com/vanillabp/business-cockpit/wiki/Security#who-sees-which-workflow) |
| A user sees a task you meant to keep from them | `admittedUsers` is the stronger of the two rules and beats `excludedCandidateUsers`. What such a reader may then do is the workflow module's question. | [Who sees which user task](https://github.com/vanillabp/business-cockpit/wiki/Security#who-sees-which-user-task) |
| A workflow module is reachable for every logged-in user | `/wm/**` is not authenticated by the cockpit's own chain. The module behind it reads the cookie and builds its own context, so a module which checks nothing checks nothing. | [Reaching a workflow module](https://github.com/vanillabp/business-cockpit/wiki/Security#reaching-a-workflow-module) |
| `Unsupported UiUriType`, `Could not load module!` or `Failed in last attempt: …` in the browser console | The browser loads the form from the module through module federation. `ui-uri-type` and `ui-uri-path` say how it is served. | [The build](https://github.com/vanillabp/business-cockpit/wiki/User-task-forms-and-status-sites#the-build) |
| No `Register microservice proxy for workflow module` line, and forms which do not load | The module never registered itself. The registration is an outbox entry, so it waits while the cockpit server is down. | [How a module registers itself](https://github.com/vanillabp/business-cockpit/wiki/Connecting-a-workflow-module#how-a-module-registers-itself) |
| A task opens a page of another system and the user logs in a second time | `ui-uri-type: EXTERNAL` opens your address in a window of its own. The cockpit does not proxy that system and says nothing about the user. | [When the cockpit cannot load your pages](https://github.com/vanillabp/business-cockpit/wiki/User-task-forms-and-status-sites#when-the-cockpit-cannot-load-your-pages) |
| `Lost server connection, will rety in 15 seconds` in the console, over and over | The live-update stream is torn down and reopened. A read timeout on the outbound HTTP client of the proxy does this, because a streamed response is idle between events. | [the upgrade skill](../../business-cockpit-upgrade-to-blocking/SKILL.md) |

## Problems the Business Cockpit only inherits

These come from your build, your database or your identity provider. They show up around the
cockpit often enough to be worth a row.

| What you see | What it is | Where it is answered |
|---|---|---|
| `ObjectOptimisticLockingFailureException` or `StaleObjectStateException` in a transaction of your own | The version attribute did its job against a report of a remote engine. This is ordinary database work between two writers of one row. Neither the write nor the exception comes from VanillaBP. | [When a read fails on a version conflict](https://github.com/vanillabp/business-cockpit/wiki/Architecture#when-a-read-fails-on-a-version-conflict) |
| `spring.data.mongodb.*` is ignored and the cockpit reports the URI as missing | Spring Boot 4 moved these settings, so the key version 1 used is not read at all. Write `spring.mongodb.uri`. | [What the cockpit server needs](https://github.com/vanillabp/business-cockpit/wiki/Configuration#what-the-cockpit-server-needs) |
| A Freemarker error on a `LocalDate` or an `OffsetDateTime` in a title | Freemarker cannot read `java.time` by itself. Put `no.api.freemarker:freemarker-java8` on the classpath. Version 1 required that library from everybody. | [What a template is handed](https://github.com/vanillabp/business-cockpit/wiki/Templates#what-a-template-is-handed) |
| Fewer live updates than expected on Azure Cosmos DB | Cosmos DB delivers fewer change events than MongoDB does, and how durable a write is comes from the consistency level of the account. `mongodb.mode: AZURE_COSMOS_MONGO_4_2` tells the cockpit about the first half. | [What the cockpit server needs](https://github.com/vanillabp/business-cockpit/wiki/Configuration#what-the-cockpit-server-needs) |
| Every open live-update stream and every proxied request holds a platform thread | `spring.threads.virtual.enabled` is off. Nothing reports it, because the application runs either way. | [What the first start tells you](https://github.com/vanillabp/business-cockpit/wiki/Running-the-Business-Cockpit#what-the-first-start-tells-you) |
| Reactive types in a customized cockpit which no longer compile | The container moved from WebFlux to Spring MVC on virtual threads with `0.8.0`. That upgrade has a skill of its own. | [business-cockpit-upgrade-to-blocking](../../business-cockpit-upgrade-to-blocking/SKILL.md) |
